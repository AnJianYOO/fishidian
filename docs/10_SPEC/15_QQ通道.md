# 15 QQ 通道

> 状态：已确定 ｜ 最后更新：2026-11-10 ｜ 对应版本：通用

手机 QQ 上跟她说话，走的是一条本地三段链路。这一段只写**现在实际是什么样**，试错过程在归档的 `19_大肥鱼窗口与双实例.md` 第 8 节和 `13_QQ接入方案.md`。

## 1 链路

```
手机 QQ ⇄ QQ 进程（NapCat 注入，OneBot v11 客户端）
              │  反向 WebSocket，由它主动连上来
              ↓
        127.0.0.1:6700（桥在监听，不是 NapCat 在监听）
              ↓
        dsh-qq-onebot-bridge ──→ 她的 DSH 实例
              ↑
        127.0.0.1:8799  qq-qrcode-server（只做二维码和状态）
```

**方向容易记反**：桥是 `WebSocketServer`（`lib/onebot.js` 里 `new WebSocketServer({host,port})`），NapCat 作为客户端反向连进来。所以"6700 有没有 Established"就是"NapCat 有没有连上"，也约等于"QQ 有没有登录"。

## 2 端口

| 端口 | 是谁 | 怎么判断活着 |
| --- | --- | --- |
| 6099 | NapCat WebUI | 浏览器能打开 |
| 6700 | 桥的 OneBot 入口 | `Get-NetTCPConnection -LocalPort 6700` 有 Established 才算连上 |
| 8798 | 桥的入站 webhook | `netstat` 里有 `127.0.0.1:8798 … LISTENING` 即已挂上，trace 里对应「入站 webhook 已监听 127.0.0.1:8798」。插件的 proactive/intel 经这里直达 QQ，不烧模型。 |

### 桥的代码在磁盘上有三个副本

「大肥鱼」窗口真正加载的是**第三份**，`--user-data-dir` 换不掉它：

| 副本 | 位置 | 谁在用 |
| --- | --- | --- |
| 调试/中转副本 | `%USERPROFILE%\dsh-qq-onebot-bridge\` | 手动排查时用 |
| 源码副本 | 开发者本地的 `dsh-qq-onebot-bridge\` | 打包器 `tools\build_v1_package.py` 从这份取 |
| **被加载的那份** | `%USERPROFILE%\.dsh-fatfish\profiles\desktop\node_modules\dsh-qq-onebot-bridge\` | 窗口运行时装的是它；pnpm 装的**独立拷贝，不是软链接** |

改了前两份、漏了第三份，重启后跑的仍是旧代码，现象是「改了、也重启了、还是老样子」。2026-11-14 排查分条发送时踩过一次：前两份都改好并重启了窗口，分条却依旧不生效，最后发现加载路径是 `node_modules` 里那份。**三份都覆盖之后再重启。**

重启命令的关键是 `DSH_HOME`，只传 `--user-data-dir` 会开成主工作窗口：

```powershell
$env:DSH_HOME = "$env:USERPROFILE\.dsh-fatfish"
Start-Process -FilePath "$env:LOCALAPPDATA\Programs\DeepSeek Harness\DeepSeek Harness.exe" `
              -ArgumentList "--user-data-dir=$env:USERPROFILE\.dsh-fatfish\electron-data"
```

起来后的三条判据：窗口标题是「大肥鱼」、8798 在 LISTENING、6700 有 ESTABLISHED。三条齐了才算桥真的跑起来。
| 8799 | 二维码/状态小服务 | `GET /status` 回 `{"ok":true}` |

## 3 白名单：谁能让它开口

判定在 `lib/bridge.js` 的 `#allowed()`，几个口径：

- **空 = 全部拒绝**。`allowUsers` 为空时私聊一条都不回，`allowGroups` 为空时群一条都不回。这是刻意的安全默认。
- `allowAllChats = true` 时全放行，两个白名单失效，但**群里的 @ 门槛不变**。
- 群消息要求群号在 `allowGroups`，且当 `allowUsers` 非空时**发送者也要在 `allowUsers`**。
- 白名单在**建会话之前**就拦掉了，不在名单里的会话根本不会被创建。所以它不会"回一句拒绝"，而是在 trace 里记一条「白名单」。排查要查 `/为什么`，别等它说话。
- **出口也查**：主动发消息、撤回、贴表情之前，目标也要在白名单里（`lib/bridge.js` 1203 行附近）。否则第三方能借它去骚扰名单外的人，风控打的是机器人账号。

面板里 `allowUsers` / `allowGroups` 必须是**数字数组**，写成字符串 `"2000000001"` 会永远匹配不上。

## 4 断线重连

反向 ws，连接由 NapCat 发起。桥这边不主动拨号，所以要重启的是 NapCat，不是桥。

重连之后 NapCat 可能把同一条消息重投一次，靠 `dedupEnabled`（默认开）+ `dedupWindowSeconds` 去重。**这个开关关了会看到重复回复。**

## 5 分条发送

一轮回复拆成几条发，像真人打字。

**判断发生在生成时，不在发送时。** 她自己知道「这句想单独说」，就用空行把边界留在文本里；桥只负责把空行切开、逐条发出去。**桥不做任何字数推断。**

- 位置：`lib/bridge.js` 的 `#splitReply`
- 优先级：① **有空行** → 按空行切，最多 3 条（超出并进第 3 条，**不丢字**）；② **没有空行** → **整条发**，桥不猜字数、不看标点、不调 `fragment`
- 桥里没有字数阈值。v0.8.3 曾用「>24 字且 ≥2 句就切一刀」兜底，她那几轮正好都是 24~26 字，于是**每轮必被切成两条**——这正是「每句话都回两句」的来源
- 代价：她若忘了打空行，长回复会一整条发。这是有意的——那轮她没表达"想分"，该回到提示词修，不该由桥替她补
- 提示词侧：内核 `expression.py` 的 `_hint` 三档按 `fragment` 直接翻译（话碎 / 正常说 / 一句说完），并保留「想断就在中间空一行」这一句机制说明。**不写任何「不必每条都分」类的行为指导** —— 频率由参数负责（五行按情绪强度参与 `fragment`/`length` 偏移），提示词再说一遍就是重影，还会和数值对冲。
- 开关：`fishidian.splitSend`，关掉就整条发
- **任何一步失败都降级成整条发送**，不会把话吞掉
- 下游要配套：`dsh-fishidian/lib/turn-merge.js` 必须把多条 assistant 累积成一轮，只留最后一条会把前面的话丢掉

## 6 入站表情与媒体

用户发来的非文字内容，先按四种块分流（`lib/onebot.js` 的 `parseMessage`）：

| 消息段 | 去向 |
| --- | --- |
| `text` | 正文，`@` 段转成 `@名字` |
| `face` / `mface` | **转成 `[表情:名字]` 塞回正文**，黄脸用 `faces.js` 的 `FACE_IDS` 反查，商城表情优先用自带的 `summary` |
| `image` | 进 `images` 数组，私聊由 `privateImageView` 下载落盘，交识图工具看 |
| `record` | 进 `records` 数组，走语音转文字 |

**`face` 绝不能抹掉。** v0.8.4 之前 `stripCq` 用 `/\[CQ:[^\]]+\]/g` 通杀，把黄脸一起删成空格，结果是「字能看见、表情是空白」；纯表情消息 `text === ''` 又没有 `images`，会被空文本分支整个 drop。现在黄脸保留为可读文本，查不到的 id 给 `[表情:其他]` —— **宁可给不精确的名字，也不给空白**。

**两条解析路径都要处理表情。** `parseMessage` 有字符串和数组两种入口：字符串走 `stripCq`，数组走另一套 `for` 循环。**NapCat 默认发数组段**，所以只在 `stripCq` 里补是不够的——数组分支必须单独认 `face`，否则黄脸静默丢失。`mface` 与 `marketface` 是 QQ 超级表情的两种叫法，都要接。不认识的段类型写进 `others`，不许静默丢。

注意：`[表情:名字]` 只是一串字，**不是图像**。她没法从名字判断表情的具体画法，只能按中文名推断；要真正"看"表情图，得走识图通路，那是另一条链路。

### 图片她能收到，但读不了内容

**当前是 `deepseek-flash`，纯文本模型**。图会被下载落盘（`qq-images`）并作为附件挂到这一轮，但模型读不出内容。

桥里**没有** `describe_image` 这个工具——`visionToolName` 的默认值只是字符串，从来没被注册出来。v0.8.4 之前提示语照着它写「请用 describe_image 查看图片」，等于让她去够一个不存在的东西，她只能回「解不开内容、还是睁眼瞎」。

现在三处提示语（私聊图、system 的 `imageGuide`、引用图）都改成**如实告知 + 禁止编造**：

> 对方发来了图片/表情包，但你读不出图里的内容。**别假装看见了，也别编图里有什么**；按上下文接一句，或者让对方说说图上是什么。

要用真看图，必须先补上视觉能力（换视觉模型 / 接识图 API / 本地 OCR）。**在补齐之前，承认看不到比编造正确。**

## 7 8799 这个 3 行服务

只做几件事，不写文件、不碰记忆库：

- `GET /qr` → 200，`image/png`
- `GET /status` → `{"ok":true,"mtime":...}`
- `GET /qqstatus` → `{"online":true,"everOnline":true,"needQR":false,"hasQR":true,"staleQR":true,"ageSec":89,"mtime":...}`
- `GET /setup` → 首次无配置时回空壳
- `POST /save` → 落 `config\setup.json`

**`online` 的判据是「6700 上有没有 ESTABLISHED」，不是「二维码文件多新」**。旧口径拿文件年龄当判据，会出现"登录成功了反而又判定需要扫码"——因为 NapCat 登录后就不再写 `qrcode.png`，两分钟后文件自然变旧。有连接才是真的登上了。前端拿到 `online:true` 就把浮层切成成功态、1.8 秒后自动关。

**`everOnline` 是「本次启动以来连上过没有」，用来决定要不要弹框**。只有 `online` 不够：桥是 DSH 插件，窗口起来后几秒才开始监听；NapCat 反向重连又有间隔，实测一次完整的重开要二十几秒才出现 ESTABLISHED。这段时间里 `online` 一直是 false，只看当下这一刻就会在"其实早就登录了"的情况下弹出二维码，框里还只有上次那张旧码。

所以弹框判定是两条：

- 有**新鲜的码**（`hasQR && !staleQR`）→ 立刻弹。首次安装、真的需要扫码，就是这个场景。
- 只有旧码或还没码 → 最多等 60 秒（30 次 × 2 秒），任何一次看到 `online` 或 `everOnline` 就不弹。等待期间界面上根本没有框，所以等久没有代价；早弹才有代价。

`staleQR` 不再等同于"要重扫"：它只说明文件旧。浮层里照样把这张图**画出来**（早先只在"新码"分支画图，旧码分支只留一句提示，结果是个空框，用户以为坏了还得自己点刷新）。`needQR` 的语义也随之变成"从来没连上过"，不再是"此刻没连上"。

存在的唯一理由：**渲染进程读不了本地文件**（`require("fs")` 不被插件加载器认，`file://` 被 Electron 拦），必须有个东西把 PNG 吐成 HTTP。

## 8 启动顺序

`launch.ps1` 依次做四件事：

1. 定位数据目录：有 `%USERPROFILE%\fishidian\data` 用新的，没有退回 `.dsh-fatfish`（兼容期设计）
2. 起 8799（**先把旧实例杀掉再起**，否则改了服务端代码也还在跑老逻辑）
3. 设 `DSH_HOME`，开她的窗口
4. 等 1.2 秒，NapCat 没跑就 `Start-Process launcher.bat -Verb RunAs`

**顺序是「小服务 → 窗口 → QQ」**。早先的顺序是「QQ → 小服务 → 窗口」，结果黑框和 UAC 先盖在桌面上，窗口要等 3 秒才动，观感是"先弹黑框，再轮到她"。现在是窗口先露头，浮层先弹出并显示"正在把 QQ 拉起来，等几秒"，码一写出来就自动填进去。

**UAC 免不了**：NapCat 要注入 QQ 进程，这是 Windows 的硬规则。想彻底免掉只能做成"最高权限运行"的计划任务，属于改系统状态，没动。NapCat 的控制台黑框也是它自己，关掉 QQ 就断。
