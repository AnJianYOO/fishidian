## 1 备什么

| 对象 | 备不备 | 说明 |
| --- | --- | --- |
| `workspace\memory\dfy.db` | **必备** | 她的全部记忆，坏了就是几个月的东西没了 |
| `workspace\sessions` | 备 | 对话记录，和记忆互相印证 |
| `config\` | 备 | persona 和设置，丢了性格就变了 |
| `workspace\files` | 不备 | 图片视频，量大，用户自己的文件他自己有 |
| `logs\` | 不备 | 排查用的，不是资产 |
| `data\profiles` | **绝不备** | 里面是 token 和 QQ 登录态，备份它等于多一份泄露面 |

## 2 怎么备：只能走 sqlite backup API

**绝不能用 `copyfile` 直接拷 `.db`。**

WAL 模式下有已写入但未 checkpoint 的内容，直接拷文件会得到一个"少了最近几条"的库，而且**不报错**——你打开它一切正常，只是记忆停在半小时前。这种坏法最难发现。

正确做法：

```python
src = sqlite3.connect(f"file:{SRC}?mode=ro", uri=True)   # 只读打开
dst = sqlite3.connect(DST)
with dst:
    src.backup(dst)
```

## 3 分几层，留几份

| 层 | 命名 | 留 | 谁生成 |
| --- | --- | --- | --- |
| 日备 | `dfy.bak-YYYYMMDD-HHMMSS` | 7 | 每天首次启动 |
| 周备 | `dfy.week-YYYY-Www` | 4 | 从当天校验通过的日备复制，一周一次 |
| 月备 | `dfy.month-YYYY-MM` | 1 | 同上，一月一次 |
| 人工留档 | `*_manual` | **永不清理** | 用户或程序在关键操作前建 |

三条硬规则：

1. **排序看文件名里的时间戳，不看 mtime。** 备份被复制或恢复后 mtime 会变新，按 mtime 排会让真正最老的那份逃过清理。
2. **周备/月备不挂"永不清理"后缀。** 它们本身就是长期层，再挂保护会让清理永久失效、越积越多。
3. **备份放 `backup\` 子目录，主数据目录只放数据文件。** 否则"今天备份过了没有"的判断会被同目录的别的文件干扰，日志会误报。

`tools\backup_live_db.py` 已经支持这套参数：

```
python -X utf8 tools\backup_live_db.py --keep 7 --keep-week 4 --keep-month 1 --prune-dry-run
```

`--prune-dry-run` 只报要删谁，不动手。**先跑这个确认名单对，再跑真的。**

## 4 什么时候跑

不能只靠定时器。笔记本会睡眠、会关机、会拔电源，定时器错过就是错过。

三层触发：

1. **每次启动时检查**——距上次成功备份超过 20 小时就补一次。这条最可靠，覆盖所有"错过"的情况
2. **连续运行跨过凌晨**——补一次日备
3. **关键操作前强制备份**——升级、卸载、导入、换号，全部先备到 `manual\`

## 5 每个备份都要验

**有个文件不等于有备份。** 每次备份完立刻做两件事：

1. `PRAGMA integrity_check`，不是 ok 就删掉这份重来
2. 记下条数（`SELECT count(*) FROM memories` 之类），写进文件名旁边的 `.meta` 或日志

备份时顺手记条数，回档的时候才有依据判断"这份是不是好的"。

## 6 回档

入口：设置页或托盘「从备份恢复」。

流程：

1. 列出可用备份：日期 + 大小 + 记录条数 + 完整性状态
2. 用户选一份
3. **先把当前库整份备份到 `backup\manual\`**——回档本身也是一次数据丢失，不留退路会把仅存的也弄没
4. 停掉所有写库的进程
5. 替换 `dfy.db`
6. 重启她
7. 报告"恢复到 X 月 X 日那份，里面有多少条记忆"

第 3 步是这条流程里最重要的一步。**没有它，回档就成了第二次事故。**
